Ceremony that fits the problem

A bug fix shouldn't turn into sixteen acceptance criteria. Three sizes of work, three paths. Start with the loop; grow into the spec graph when you want it.

Why OneSpec

Spec-driven development without the paperwork. Everything here earns its place.

Specs that stay true

Each change folds back into durable specs when it is done, so the specs describe the product as it is meant to be, not as it was planned months ago.

Light by design

One prose file per change. A bug fix is one patch. No tool beyond the skills, and no Markdown pile-up to review.

One step at a time

Plan only the next increment in detail. Everything after it stays a one-line backlog item, and each plan starts from what the last build taught you.

Proof, not promises

Every build declares its acceptance check up front and records the evidence that it delivered. Tests fail before and pass after.

And a few more good reasons

You stay in control

Every build stops at your checkpoint. Checks only you can make are listed as author actions, and the build waits for them.

Traceable both ways

Code and tests point to the spec section they implement. Reviews show what's covered, what's a gap, and what the code does that no spec describes.

Less to review

One file per change, in ordinary prose and a fixed order. One build plan per checkpoint, one commit per patch.

No tool lock-in

Specs are plain Markdown in your repo. Install the skills with npx skills add or the Claude Code plugin marketplace.
